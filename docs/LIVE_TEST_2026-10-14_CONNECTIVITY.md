# 网络连通检测调整

用户要求这些卡片只判断网络是否可达及显示延迟，不做网站功能、地区解锁或 Cloudflare 拦截诊断。

现在只要取得有效 HTTPS 响应和正数耗时，就显示绿色「网络可达」，包括 HTTP 403、429 和 5xx。HTTP 状态保留在诊断提示，不占卡片主位置，也不计成网络失败。超时、TLS 验证失败、无效耗时及面板接口错误仍显示失败，不能拿这些情况当成功。

这里的毫秒数是现有 HTTPS 请求耗时，包含连接建立和等待响应，不是 ICMP ping 或单纯节点 RTT。检测请求、时间上限和顺序队列沿用现有实现；没有加入 CF 识别、备用请求、常驻进程或更多并发。

同时修正所选出站检测的模式顺序：全局模式国内外站点都测 GLOBAL，直连模式都测 direct。AX5 继续通过内核混合端口按实际规则请求；K2P 使用核心出站检测接口，不能将其结果当作真实 LAN 域名分流证明。

实机验证：两机各8个目标均显示可达。AX5 ChatGPT实际返回403，显示「网络可达 /1195ms」；K2P ChatGPT出站检测662ms。两机1200px及390px页面没有水平溢出、脚本异常；内核PID、模式和部署前设置指纹保持不变。没有重启服务或改变用户的节点选择。耗时是这一次样本，不是持续性能保证。

离线验证：403/429/503分类、TLS与接口错误、无效时间、模式目标和DOM卡片回归通过。全套AX5 69个Python用例及22个JS脚本、K2P163个Python用例及24个JS脚本、根33项和构建/迁移基线通过。DOM新增回归在最终构建单独执行通过。原始截图与响应在私有工作目录，不纳入公开资产。

控件执行表继续标记部分通过：本轮没有逐端点在两端注入每种网络故障、取消和全部模式组合。整个项目的OOM与其他上线验收门槛仍未关闭，不发布候选。

K2P 已在保护阈值以上额外预留6MB后保存Storage，压缩包518920字节；核心PID30205未变。两机检测后全部配置文件与部署前指纹再次核对一致。没有发布新版本。
